# نقشه اجرایی AI Router Studio
آخرین بازبینی: 2026-10-14
شاخه کاری: `ai-router-v1`

## 1. هدف محصول
ساخت یک ارکستراتور هوش مصنوعی که درخواست طبیعی کاربر را به یک طرح شفاف و قابل‌ویرایش تبدیل کند، Taskها را بین ابزارها/مدل‌های مناسب تقسیم کند، هزینه را صفر نگه دارد، Context و توکن را کاهش دهد و تنها پس از تأیید کاربر کارهای ساختنی را اجرا کند.

## 2. محدودیت‌های قطعی
- سقف هزینه پیش‌فرض و نسخه اول: صفر تومان؛ هیچ Provider پولی نباید فراخوانی شود.
- هیچ Task نباید «موفق» اعلام شود مگر نتیجه واقعی و قابل بررسی دریافت شده باشد.
- Preview و تأیید کاربر پیش از ساخت/تغییر/حذف/انتشار الزامی است.
- پس از هر تغییر مهم در Plan، تأیید قبلی باطل می‌شود.
- اول ابزار آماده و رایگان را بررسی می‌کنیم؛ فقط کمبود واقعی را خودمان می‌سازیم.
- استفاده از API فقط پس از بررسی رایگان بودن، سهمیه، دسترسی منطقه‌ای، شرایط استفاده و روش امن نگهداری کلید.
- هیچ رمز، API key یا access token داخل مخزن Git نرود.
- رشد اینستاگرام باید بر محتوای مجاز، آمار دسترس‌پذیر و مخاطب داوطلبانه متمرکز باشد؛ بدون scraping یا پیام انبوه ناخواسته.

## 3. وضعیت واقعی فعلی
### موجود
- رابط استاتیک فارسی RTL در `ai-router/index.html`

- Preview وظایف
- تخمین توکن تقریبی بر پایه طول متن
- دکمه تأیید و شبیه‌ساز وضعیت اجرا
- فایل تنظیمات اولیه Providerها

- شمارش دقیق توکن با tokenizer هر مدل
- Cache یا حافظه پایدار
- اجرای واقعی Taskها و تست نتیجه
- Research و مدیریت citation
- تولید تصویر
- اتصال Instagram/Meta
- انتشار Pages تأییدشده

## 4. تصمیم معماری
### انتخاب پیشنهادی: Local-first + adapterهای قابل تعویض
- Frontend: رابط فعلی HTML/CSS/JS را تا وقتی نیاز واقعی به framework ثابت نشده حفظ کنیم.
- Orchestrator: backend سبک محلی (ترجیحاً Python برای ادغام مدل/تحقیق؛ Node فقط اگر ساده‌تر ثابت شود). انتخاب نهایی بعد از prototype و بررسی dependencyها.
- Model routing: ابتدا ارزیابی LiteLLM SDK به‌عنوان لایه اتصال چند Provider؛ برای نسخه تک‌کاربره از راه‌اندازی LiteLLM Proxy، Redis یا زیرساخت سنگین پرهیز شود مگر نیاز اثبات شود.
- Local inference: بررسی نصب/وضعیت Ollama و اجرای یک مدل کوچک روی دستگاه، بدون تضمین عملکرد پیش از benchmark واقعی.
- Visual workflow platform: Dify فقط جایگزین احتمالی اگر workflow بصری مزیت روشن بدهد؛ Dify و LiteLLM و n8n را همگی با هم وارد نسخه اول نکنیم.
- Persistent state/cache: SQLite + cache محلی ساده، پس از شروع backend.
- Deployment: GitHub Pages فقط برای UI استاتیک؛ هیچ کلید API یا backend خصوصی در آن قرار نمی‌گیرد. Backend محلی در شروع؛ هاست backend رایگان تنها اگر محدودیت و دسترسی آن تأیید شود.
- Providers: adapter interface شامل capabilities، availability، quota/cost policy، token estimate، execute و structured result.

## 6. سیاست صرفه‌جویی توکن
- مدل کوچک/قانون‌محور برای طبقه‌بندی ساده و routing تا وقتی کیفیت کافی دارد.
- یک بار استخراج مشخصات؛ نه اینکه هر Worker کل درخواست و تاریخچه را دوباره دریافت کند.
- Context اختصاصی برای هر Task و ارسال فقط فایل/منبع لازم.
- خروجی‌های ساخت‌یافته و محدودشده با JSON schema و سقف خروجی.
- خلاصه‌سازی بین Workerها، همراه با پیوند به منابع اصلی برای جلوگیری از حذف شواهد.
- Cache فقط وقتی ورودی، مدل، نسخه prompt و پارامترها با هم سازگارند؛ برای تحقیق تازه و داده زودمنقضی TTL داشته باشد.
- parallelization فقط برای Taskهای مستقل؛ تعداد Workerها محدود تا درخواست تکراری ایجاد نشود.
- verifier فقط برای Taskهای پرریسک/مهم یا نمونه‌برداری براساس کیفیت.
- token count دقیق از خود provider/tokenizer هرگاه موجود باشد؛ در غیر این‌صورت تخمین به‌صورت بازه و با برچسب «تخمینی».
- هیچ درصد صرفه‌جویی بدون benchmark واقعی اعلام نشود.

## 8. خطرها و کنترل‌ها
- Provider رایگان ممکن است در دسترس نباشد یا محدودیت منطقه‌ای داشته باشد → قبل از اتصال تست شود، هیچ دورزدن محدودیت یا هزینه خودکار انجام نشود.
- مدل محلی ممکن است کند باشد → benchmark قبل از تعهد به آن.
- خروجی علمی نادرست → citation/evidence checker و گزارش عدم قطعیت.
- Prompt injection از وب/فایل/Skill → محتوای خارج از سیستم داده نامطمئن تلقی شود؛ دستورهای داخل منابع اجرا نشوند.
- XSS/افشای secrets → ورودی‌ها escape، کلیدها فقط سمت backend.
- انتشار ناخواسته → تأیید صریح جداگانه برای deploy/publish/delete.
- scope creep → یک end-to-end path را کامل کنیم قبل از افزودن ابزار و Provider جدید.
